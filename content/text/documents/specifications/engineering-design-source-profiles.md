## Source-owned requirement conditions

**The original source-bound Engineering Design provider and its receiving owners MUST** ensure that the existing Specification Engineering ./engineering-design provider is the one general source-bound Design engine. Its original planEngineeringDesign, receiveEngineeringDesign and readEngineeringCodeWork producer/consumer family is completed in place; no parallel Scheme designer, JS wrapper around Scheme, copied provider or second package is introduced. (Original Requirement engineering-design-accepts-explicit-source-profiles (ni:///sha-256;oJBTBcQ8qRwN78ZGaPuAtLN1zTApV_geIhvgRZkrvhQ), cell engineering-design-accepts-explicit-source-profiles:original-owner).

**The original source-bound Engineering Design provider and its receiving owners MUST** ensure that every Design plan, receiving request and Code Work readout selects one explicit source-language/artifact profile as a checked parameter. A missing, malformed, ambiguous or changed profile refuses before inference or Code Work projection. The API offers no implicit JavaScript profile, old-call fallback, alias or compatibility shim. (Original Requirement engineering-design-accepts-explicit-source-profiles (ni:///sha-256;oJBTBcQ8qRwN78ZGaPuAtLN1zTApV_geIhvgRZkrvhQ), cell engineering-design-accepts-explicit-source-profiles:explicit-profile).

**The original source-bound Engineering Design provider and its receiving owners MUST** ensure that the profile carries finite literal data identifying the source language/artifact role and its normalized module path, extension, symbol-spelling and resource constraints. The engine validates the profile at its boundary and checks source names against that selected policy. A profile cannot introduce a callable parser, arbitrary executable grammar, regular-expression program, shell command, dynamic import, host path, authority flag or effect grant. (Original Requirement engineering-design-accepts-explicit-source-profiles (ni:///sha-256;oJBTBcQ8qRwN78ZGaPuAtLN1zTApV_geIhvgRZkrvhQ), cell engineering-design-accepts-explicit-source-profiles:data-policy).

**The original source-bound Engineering Design provider and its receiving owners MUST** ensure that the same engine can plan and receive existing JavaScript module/export targets and native Scheme source/symbol targets, including the original CDE src/, scripts/ and test/ source roles, through their respective explicitly supplied profiles. It does not silently rename a target, translate Scheme into JavaScript or treat a profile label as proof that a parser or source file exists. (Original Requirement engineering-design-accepts-explicit-source-profiles (ni:///sha-256;oJBTBcQ8qRwN78ZGaPuAtLN1zTApV_geIhvgRZkrvhQ), cell engineering-design-accepts-explicit-source-profiles:general-names).

(Original Requirement engineering-design-accepts-explicit-source-profiles (ni:///sha-256;oJBTBcQ8qRwN78ZGaPuAtLN1zTApV_geIhvgRZkrvhQ), cell engineering-design-accepts-explicit-source-profiles:profile-source-binding).

## Actual Design-to-inference schema handoff — source-bound refinement (2026-10-29)

This is a **proposed receiving contract at the original owner**, derived from the original 13-cell Requirement's `profile-source-binding`, `native-receiving` and `source-and-operation-evidence` conditions, **not** an LLD, a new inference adapter, provider consent, Work grant or the completed independent review. The unchanged rejected first LLD remains negative evidence. Reuse the existing native Design caller and the original Computer Inference Engine (CIE) input/dispatcher; do not change its original plan or infer a failed transport from a failed output.

**Three distinct source/operation boundaries must be checked separately.** (1) At the original Design owner, `planEngineeringDesign` currently returns `request.schema` and `requiredCapabilities:['text-output']`; `receiveEngineeringDesign` re-derives that *entire exact plan* to enforce the source cut. A source-pinned plan schema is a proposal/receiving contract, **not** yet a provider request. (2) At the original native host caller, a separately reviewed actual invocation must witness that its CIE `input.outputSchema` is structurally and content-identical to the selected `plan.request.schema`, that a deliberate `input.enforceProviderSchema===true` is carried when provider enforcement is required, and that its `requiredCapabilities` *also includes* `json-schema-output` for this particular strict-output attempt. The latter is necessary because the incumbent CIE does **not** add that required capability merely because `enforceProviderSchema` was set. Keep the source/plan/Work/selected profile/transport identities and authorization unchanged; do not let a profile nominate a provider or spending account. (3) At the original CIE selected-offer/transport/recipient boundary, read the **actual selected descriptor** and effective `response_format`, not the present catalog label or source plan. An advertised `json-schema-output` descriptor and `enforceProviderSchema` are both necessary for CIE's direct-lane `json_schema` response-format construction. CIE's `strict:true` predicate is a recursive closed-object check; it is **not** an independent full JSON Schema grammar checker. Preserve original customer-side output assay regardless of any provider-side shaping. The `chatCompletion.response_format` override is a distinct original precedence path that must show exact source/schema equality and its capability contract rather than bypass this check.

**Read-only pre-effect refusal oracle (original CIE/Design owners):** refuse or classify **unknown** if the native caller's schema projection, exact source/profiles, selected descriptor capability, effective wire `response_format` or original consumer receipt is absent, stale, ambiguous or inconsistent. A schema present only in `plan.request.schema`, an `outputSchema` with `enforceProviderSchema` absent/false, or a descriptor lacking `json-schema-output` does not witness provider constraint. A recursively open schema cannot be reported as strict; a syntactically malformed nested schema may still satisfy CIE's structural closedness predicate and must first pass the incumbent JSON Schema owner. A `chatCompletion` override differing from the plan's original schema refuses as source-cut mismatch; the original `receiveEngineeringDesign` must still refuse root schema-definition members `type,additionalProperties,required,properties` in a supposed three-key LLD *instance*. Check positive HLD and LLD closed schemas, opened nested objects, wrong/missing CIE fields and selected capable/incapable providers independently. Never transform the first raw output or silently retry its original paid/zero-cash lot.

**Native receiving after source review:** The original CIE outcome owner must reconcile its own work-lot journal and record the original negative verdict only under its original receiver authority, then recover the **actual first request envelope** and provider-evidence/transport receipt. The previously selected model's returned identity is not sufficient to reconstruct whether the original adapter supplied `outputSchema`, `enforceProviderSchema`, `json-schema-output` or an effective `response_format`.
